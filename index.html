Envarsa — a local-first library for your environment variables.

Env values scatter across projects and machines, get silently duplicated, and die with a disk. Envarsa gives them one home: capture a project’s .env as a point-in-time snapshot, recall it with values masked, and hand values back — by clipboard or export — when you need a project working again.

# the problem

Your .env files lead short, scattered lives

They sit untracked at the root of every project — ignored by git on purpose, and by everything else by accident.

Scattered

One per project, per machine, per half-finished experiment. Six months later, the API key you need is in a folder you deleted.

Silently duplicated

The same DATABASE_URL pasted into five projects. One of them got rotated. Which one is right is now archaeology.

Mortal

No backups, no history, no sync — a dead disk or an overeager cleanup takes them along, and they were the one thing you couldn’t re-clone.

# how it works

Capture, recall, hand back — a librarian’s loop

By default Envarsa is a store-only librarian — it organizes, copies, and exports without touching your project tree, and it never injects variables into processes. When you ask, it writes a .env*.local on a path you choose (never a committed example file). “Use these values” always means you place them.

01Capture

Import a .env via file picker, paste, or drop it on the window. Comments, blank lines, even unparseable lines are kept byte-for-byte. Capture is manual — a snapshot is a moment in time, and Envarsa never watches your files.

02Recall

Find the project by the name you chose (paths are non-binding hints). See keys, comments, history. Duplicate keys are tagged overridden; keys shared with other projects carry a reuse badge — same value or different — but editing one place never propagates anywhere.

03Hand back

Copy one value — it travels core → clipboard without ever rendering on screen — copy the whole block, or export a .env wherever you choose, byte-identical to what was captured. Copies stay out of Windows clipboard history and clear themselves after 30 seconds.

04History

Every capture appends a snapshot. View older ones read-only, or bring one back as latest. Yesterday’s working configuration is a click away, not a memory exercise.

05Write a .env.local

When you do want a file back, write a snapshot to a .env*.local in a folder you pick — merge to fill in keys while keeping the file’s own comments and structure, or fresh to replace it outright. A preview counts what will be added, updated, kept, or blanked before a byte lands. Point it at a .env.example instead and Envarsa scaffolds a .env.local beside it from the template’s keys and comments — placeholders are blanked, never copied. A committed example file is refused, every time: only a .env*.local is ever writable.

06Build it by hand

Or never touch a file at all. Open the structured editor with no import, type keys, values, and # comments into a form, name it, and save — the project lives entirely in the store. Edit a snapshot the same way and it saves as a new snapshot, the old one kept in history. Keys are validated before the snapshot is created. A project is always yours in the store, with or without a file on disk.

# the store file

Everything lives in one file you own

  • Plaintext, pretty-printed JSON by default. Read it, diff it, back it up with any tool you already trust. Captured .env text is embedded verbatim.
  • Durable by construction. Every save is atomic — temp file, fsync, rename — and keeps a one-step .bak sibling. A corrupt store is never overwritten; the app offers the backup instead.
  • Optional encryption at rest with a passphrase, in the standard age format (scrypt). The promise survives the tool: the reference CLI decrypts it. No recovery from a lost passphrase — which is why it’s opt-in.
  • Portability is manual and yours. Export a copy — optionally encrypted for transport — and import it elsewhere; projects merge, name conflicts are flagged per project. Or keep the live file in a folder you sync yourself.

# security, honestly

What the masking is — and what it isn’t

No theater. Masking is a shoulder-surfing defense, not encryption. The baseline secrets boundary is your full-disk encryption — the same boundary as the plaintext .env files you already keep.

Structural masking, not heuristics

An entry is an env var: its key is always visible, its value is always masked until you reveal it, one value at a time. Revealed values auto-hide after 30 seconds and whenever the window loses focus. Even unparseable lines are masked — a malformed line is as likely as any to hold a secret.

A sandboxed UI that never sees more than it must

The webview is restricted to the app’s own commands (CSP default-src 'self'). Values cross into the UI only on explicit per-value reveal — single-value copies never transit the UI at all. No registered command takes a filesystem path from the webview: dropped files are read on the Rust side, and store imports are keyed by an opaque token minted when you pick the file.

A clipboard that forgets

Copies clear themselves after 30 seconds if the clipboard still holds what was copied; on Windows they are also marked to stay out of the clipboard history (Win+V) and the cross-device cloud clipboard. Linux has no equivalent exclusion flag: a clipboard manager (Klipper, CopyQ, a GNOME extension) records a copy the moment it lands, and the 30-second clear doesn’t purge the manager’s own history — pause it or clear it after copying a secret.

Concentration, mitigated

Envarsa does concentrate values into one file. That trade is made explicit and defended: masking in the UI, atomic saves with a backup, and opt-in passphrase encryption at rest.

The network surface: one opt-in update check

Out of the box Envarsa makes no network calls at all. The single deliberate exception to no-egress is the update check, off by default: a GET to api.github.com for the latest release tag, made only when you click Check for updates or opt into the daily check. The reply is treated as untrusted input — nothing but a semver-validated version number is used — and nothing downloads or installs itself. All of it lives in one module, the app’s entire network surface.

# faq

Questions, answered plainly

Does Envarsa send my values anywhere?

No. Your values live in one file on your disk and never leave unless you export them yourself. The single deliberate exception to no-egress is the opt-in update check, off by default: one GET to api.github.com for the latest release tag. It transmits no values, nothing downloads or installs itself, and it is the app’s entire network surface.

Is the store encrypted?

By default it’s plaintext, pretty-printed JSON — you own the bytes and can read, diff, and back them up with any tool. You can opt in to passphrase encryption at rest in the standard age format (scrypt); the file then also decrypts with the reference CLI. There is no recovery from a lost passphrase — exactly why it’s opt-in.

Does Envarsa write into my projects or inject environment variables?

Only when you ask. It never injects variables into processes, and by default it’s a store-only librarian: it organizes, copies, and exports without touching your tree. The one exception is an explicit, user-initiated write — a .env*.local on a path you choose, in merge or fresh mode, or scaffolded from a .env.example. A committed example file (.env.example, .sample, .template, .dist) is always refused, and the path is resolved and guarded in Rust, never taken from the webview. Using a value always means you place it.

Which platforms does it run on?

On Windows 10 and 11 (x64), as a per-user installer or a portable zip — both need the WebView2 runtime, preinstalled on Windows 11 and on any Windows 10 kept current. On Linux (x64), as an AppImage — webview bundled, runs on any distro with glibc 2.35+ (Ubuntu 22.04+, Debian 12+, and peers) — or as a Debian package that pulls its dependencies from apt.

Why is every value masked, even boring ones like PORT?

Because masking is structural, not heuristic. Envarsa never guesses what counts as a secret — even unparseable lines are masked, since a malformed line is as likely as any to hold one.

What happens if the store file gets corrupted?

Every save is atomic (temp file, fsync, rename) and keeps a one-step .bak sibling. A corrupt store is never overwritten; the app offers the backup at startup — restoring is only possible from that corrupt-store gate, never against a healthy session.

How do I move my library to another machine?

Portability is manual and yours. Export a copy from Settings — optionally age-encrypted with a transport passphrase — and import it on the other machine: its projects merge into the library there, with name conflicts flagged per project (replace, rename, or skip). Or keep the live store file in a folder you sync yourself.

Is Envarsa free and open source?

Yes — MIT-licensed, with the full source on GitHub: a no-build ES-module frontend over a Rust core (Tauri 2).

Three things to know up front

  • The Windows builds need the WebView2 runtime — preinstalled on Windows 11 and on any Windows 10 kept current. The portable build doesn’t fetch it; if the app won’t start, install it from Microsoft. The Linux builds bring their own webview: bundled in the AppImage, pulled by apt for the .deb.
  • The binaries are unsigned — first launch on Windows shows a SmartScreen prompt: More info → Run anyway.
  • Portable means no install, not data-on-a-stick — the store lives in %APPDATA%\com.envarsa.app (Linux: ~/.local/share/com.envarsa.app), not next to the exe. Repoint it in Settings if you want it somewhere you sync.
